# Svarog 流式分析与精简报告设计

## 目标

在保持每条有效日志都经过本地规则判断的前提下，将 `analyze` 改为单遍流式处理，并让报告默认只保留有证据的风险事件。正常事件的本地置信度从 `0.20` 调整为 `0.04`，报告明细始终有固定上限，避免日志量增长时内存和输出文件同步膨胀。

本设计是已确认路线中的第 1 步。第 2 步“自动评测”和第 3 步“多日志关联”只在本设计中预留稳定统计与事件标识，不在本次实现范围内。

## 当前问题

当前 CLI 先把整个 JSONL 文件解析成事件元组，再统一构建所有 `EventAnalysis`。即使最终只关心少量风险事件，正常事件也会长期保存在解析结果和报告中。对于更大的日志文件，这会造成三类问题：

- 内存随有效事件总数增长；
- 终端输出被大量正常事件淹没；
- JSON 报告体积接近原始日志，降低人工审查价值。

过滤报告输出本身不能解决解析阶段的内存增长，因此必须同时改为流式解析和逐条分析。

## 范围

本次实现包含：

- 单文件 JSONL 的逐行解析和逐条本地规则判断；
- 正常事件置信度调整为 `0.04`；
- 默认只输出有规则证据的事件；
- `--include-normal` 完整输出开关；
- 最多保留 10,000 条报告明细；
- 风险事件优先保留；
- 基于全部已分析事件的真实汇总；
- 报告截断警告和 schema 升级；
- 现有文件大小、单行大小、字段长度、Unicode 和输入问题上限继续生效。

本次明确不包含：

- 实时 `watch` 模式；
- 日志轮转和断点续读；
- SQLite、磁盘队列或后台 Windows 服务；
- 多服务器采集；
- LLM、云端 API 或网络请求；
- 自动封禁、命令执行、外部反制或身份归因；
- 自动评测命令和跨日志关联规则。

## 总体数据流

```text
JSONL 文件
  -> 逐行读取与字段校验
  -> 单条 NormalizedEvent
  -> 本地确定性规则分析
  -> 更新全局计数
  -> 按报告策略选择是否保留明细
  -> 释放未保留事件
  -> 生成有界终端和 JSON 报告
```

CLI 主路径不再调用会累积全部事件的批量解析接口。每次循环只持有当前原始行、当前标准化事件和当前分析结果。

## 流式解析接口

解析层新增单遍迭代接口，逐项产生以下两类结果：

- 有效的 `NormalizedEvent`；
- 单行对应的 `InputIssue`。

文件不存在、不是普通文件、超过文件大小上限或完全没有有效事件仍属于整体输入失败。空行继续忽略。无效行不会中断后续有效行。

现有 `parse_jsonl()` 保留兼容性，可通过消费流式接口构建旧式 `ParseResult`；CLI 和新的报告构建路径必须使用流式接口，不能通过兼容函数重新累积全部事件。

输入问题继续遵循现有规则：最多保留 1,000 条明细，额外使用一条 `issues_truncated` 记录精确省略数量，真实问题总数单独统计。

## 分析与有界保留

流式报告累加器对每个有效事件执行 `analyze_event()`，随后立即更新：

- `total_events`；
- `suspicious_events`；
- 各严重度总数；
- 输入问题真实总数；
- 正常事件过滤数；
- 报告明细截断数。

无规则证据的事件保持 `Severity.INFO` 和 `INSUFFICIENT_EVIDENCE`，置信度改为 `0.04`。该值表示当前本地规则没有发现明确证据，不表示系统被确认安全。

### 默认模式

- 正常事件完成统计后立即释放；
- 有证据的风险事件进入报告候选；
- 最多保留前 10,000 条风险事件；
- 超出上限的风险事件继续参与汇总，但计入 `truncated_detail_events`。

### `--include-normal` 模式

- 正常和风险事件都有资格进入报告；
- 总明细仍最多 10,000 条；
- 风险事件优先于正常事件；
- 如果明细已被正常事件占满，后续风险事件会替换一个正常事件；
- 如果风险事件本身超过 10,000 条，只保留按原始行号最早的 10,000 条风险事件；
- 最终明细按原始 `line_number` 排序。

这保证内存上界由配置常量决定，而不是由输入事件总数决定。

## 报告语义

默认输出中的 `events` 不再表示全部有效事件，而表示实际保留的报告明细。因此报告 schema 从 `0.1.0` 升级到 `0.2.0`。这是报告格式版本变化，不代表已经接入 LLM。

`summary` 保留原有字段并新增：

- `reported_events`：实际写入 `events` 的明细数量；
- `suppressed_normal_events`：因默认精简策略未进入明细的正常事件数量；
- `truncated_detail_events`：符合当前输出模式但因 10,000 条上限未进入明细的事件数量。

字段定义如下：

- `total_events` 始终是全部有效事件数；
- `suspicious_events` 始终是全部有证据事件数；
- 严重度计数始终基于全部有效事件；
- `input_issues` 始终是真实输入问题总数；
- `reported_events` 等于序列化后的 `events` 长度；
- 默认模式下 `suppressed_normal_events` 等于全部正常事件数；
- `--include-normal` 模式下 `suppressed_normal_events` 为零，因容量不足省略的正常或风险事件计入 `truncated_detail_events`。

只要 `truncated_detail_events` 大于零，终端和 JSON 的 `warnings` 都必须明确说明报告明细不完整，但全部输入仍已完成本地分析。

## CLI 行为

默认命令保持简洁：

```powershell
svarog analyze access.jsonl --json-out report.json
```

该命令只输出风险明细和完整汇总。需要调试全部事件时使用：

```powershell
svarog analyze access.jsonl --include-normal --json-out full-report.json
```

输入文件与输出文件同实体保护、Windows 控制台不可编码字符降级、固定中文错误和退出码语义保持不变。

## 资源边界

本次修改后的主要内存上界为：

- 当前单行原始数据：最多 1 MiB；
- 报告事件明细：最多 10,000 条；
- 输入问题明细：最多 1,000 条加一条汇总；
- JSON 序列化：仅针对有界报告对象。

文件总大小暂时继续使用 10 MiB 上限。后续实时监听版本将用文件偏移量、检查点和磁盘缓冲处理持续增长的日志，不通过提高单次文件上限代替流式架构。

## 错误与安全边界

- 完全没有有效事件时返回退出码 1；
- 部分坏行继续分析有效行；
- 达到明细上限不返回失败，但必须记录截断警告；
- 报告写入仍在严格 UTF-8 编码成功后才打开目标，避免编码失败截断旧报告；
- 日志文本始终是不可信数据；
- 本地规则未命中只表示证据不足；
- `source_ip` 只表示观测到的网络来源；
- 分析不会触发任何外部动作。

## 测试策略

自动化测试必须覆盖：

1. 正常事件置信度严格为 `0.04`；
2. 默认模式分析全部事件但只保留风险事件；
3. 全正常文件生成空 `events` 和正确汇总；
4. `--include-normal` 保留正常事件；
5. 默认模式风险事件超过 10,000 条时明细有界、汇总真实、警告存在；
6. `--include-normal` 达到上限后，后续风险事件能够替换正常事件；
7. 最终明细按原始行号排序；
8. 输入问题明细和真实计数不回归；
9. Unicode、终端控制字符、输入输出同文件保护不回归；
10. 正常、攻击和提示词注入样例行为不回归；
11. 1000 行规避测试集能够完成分析，默认报告明显小于完整输出；
12. 运行时代码仍不包含 LLM、网络请求或命令执行能力。

## 后续路线接口

第 2 步自动评测将使用 `request_id` 对报告风险明细和 ground truth 进行匹配。真实汇总与明确的报告截断字段可以让评测器区分“规则漏报”和“因明细上限未展示”。

第 3 步多日志关联将在逐条分析之后增加有界时间窗口，输出新的关联事件。它不会改变流式解析接口，也不会要求原始日志全部驻留内存。

未来 LLM 只接收本地规则或关联引擎形成的少量安全事件包，并必须具备批处理、并发限制、速率限制、超时、熔断、额度不足提醒和本地安全降级。原始日志不会逐条发送给 LLM。
