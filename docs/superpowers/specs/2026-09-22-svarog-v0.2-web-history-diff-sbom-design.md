# Svarog v0.2 Web 历史审计、差异与 SBOM 设计

**状态：** 待用户最终审阅  
**日期：** 2026-09-22  
**目标版本：** 0.2.0  
**作者：** xwikex  
**替代文档：** 本文按最新产品决策取代 `2026-09-03-svarog-phase-two-history-diff-sbom-design.md` 中与 v0.2 冲突的范围和交互约定。

## 1. 目标

Svarog v0.2 将当前的一次性依赖审计升级为可持续使用的本地审计工作台：

1. 保存轻量运行记录与去重后的内容快照；
2. 基于稳定哈希复用无变化结果；
3. 区分项目变化、知识库变化和分析引擎变化；
4. 在 Web UI 中查询、筛选和比较历史；
5. 导出符合 CycloneDX 1.7 的组件清单及尽力解析的依赖关系；
6. 继续保持单用户、本地、默认只读和不执行处置的安全边界。

JSON 数据模型仍是历史、差异和 SBOM 的权威语义，Web UI 只负责输入、展示与下载。

## 2. 已确认的产品决策

1. 审计历史库与 SOP 案件库分开；
2. 项目身份保存在 `.svarog/config/project.json`；
3. SBOM 输出所有可用组件，只输出能够确定的父子关系，绝不猜测；
4. 历史默认保留 180 天，可配置 3 至 365 天；
5. 每次成功保存或复用审计后自动清理过期历史；
6. v0.2 新功能优先通过 Web UI 提供，现有 CLI 保持兼容，不增加新的历史命令；
7. SBOM 只包含组件与依赖关系，不包含漏洞对象；
8. 差异默认比较最新成功运行与上一次成功运行，同时允许手动选择任意两个兼容快照；
9. 本地运行数据使用分类明确的 `.svarog/` 目录；
10. 采用独立领域模块，不把数据库、差异和 SBOM 逻辑堆入 Web 路由；
11. Web UI 保持简洁，不在页面中放置教程或大段使用说明；完整用户说明在版本收尾时编写。

## 6. 项目身份与设置

### 6.1 `project.json`

```json
{
  "schema_version": 1,
  "project_id": "proj_<uuid>",
  "display_name": "用户填写的项目名称",
  "created_at": "UTC ISO 8601"
}
```

- 第一次执行任何启用历史保存的环境审计或项目审计前由 Web UI 创建；
- `project_id` 创建后不随目录改名变化；
- 不包含绝对路径、用户名或主机名；
- 普通设置只允许修改显示名称；
- 删除身份文件后，UI 必须明确提示将建立新的项目身份。

### 6.2 `settings.json`

```json
{
  "schema_version": 1,
  "audit_retention_days": 180
}
```

- 合法范围为 3 至 365；
- 损坏或越界配置不会静默采用；
- 配置无效时停止历史清理，但允许只读查看已有历史；
- 修改保留期后，在下一次成功保存或复用审计后执行清理。

配置文件使用原子替换写入，POSIX 上尽力使用当前用户读写权限。Windows 不使用不可靠的标准库逻辑重写 ACL。

## 7. 旧数据迁移

检测旧位置 `.svarog/cases.sqlite3` 时：

1. 新位置不存在才允许迁移；
2. 使用 SQLite backup API 复制到 `.svarog/database/cases.sqlite3`；
3. 对副本执行 `PRAGMA quick_check`；
4. 验证通过后切换到新路径；
5. 不自动删除旧文件；
6. 失败时继续使用旧数据库并显示有界警告。

旧 `reports/` 不自动移动。v0.2 新导出写入新的分类目录，避免误处理用户文件。

## 8. 数据库管理与迁移

`DatabaseManager` 负责安全创建、连接、事务、版本检查、备份和迁移。

连接至少设置：

```text
foreign_keys = ON
journal_mode = WAL
busy_timeout = 5000ms
trusted_schema = OFF
```

数据库版本同时记录在：

- `PRAGMA user_version`；
- `schema_migrations(version, name, checksum, applied_at)`。

迁移规则：

- 新数据库直接建立最新 Schema；
- 旧数据库先复制到 `database/backups/`；
- 每个版本迁移在独立事务中完成；
- 迁移失败立即回滚，原库和备份都保留；
- 高于程序支持版本的数据库拒绝写入；
- 损坏数据库不自动覆盖或重建同名文件；
- 创建、关闭、重开和版本校验必须有冒烟测试。

## 9. SQLite Schema v1

### 9.1 `projects`

- `project_id TEXT PRIMARY KEY`；
- `display_name TEXT NOT NULL`；
- `created_at TEXT NOT NULL`；
- `updated_at TEXT NOT NULL`。

### 9.2 `audit_snapshots`

每个唯一内容快照一行：

- `snapshot_id INTEGER PRIMARY KEY`；
- `project_id TEXT NOT NULL`；
- `audit_kind TEXT NOT NULL`；
- `created_at TEXT NOT NULL`；
- `last_used_at TEXT NOT NULL`；
- `python_version TEXT NOT NULL`；
- `environment_hash TEXT NOT NULL`；
- `semantic_lock_hash TEXT NULL`；
- `knowledge_content_hash TEXT NOT NULL`；
- `knowledge_metadata_hash TEXT NOT NULL`；
- `evaluation_context_hash TEXT NOT NULL`；
- `policy_hash TEXT NOT NULL`；
- `analysis_contract_version TEXT NOT NULL`；
- `composite_hash TEXT NOT NULL`；
- `audit_status TEXT NOT NULL`；
- 有界摘要计数；
- `result_json_zlib BLOB NOT NULL`；
- `result_json_sha256 TEXT NOT NULL`；
- `result_json_size INTEGER NOT NULL`；
- `schema_version TEXT NOT NULL`。

唯一约束：

```text
(project_id, audit_kind, composite_hash)
```

### 9.3 `audit_runs`

每次用户发起审计都产生一行：

- `run_id TEXT PRIMARY KEY`；
- `project_id TEXT NOT NULL`；
- `audit_kind TEXT NOT NULL`；
- `snapshot_id INTEGER NULL`；
- `baseline_run_id TEXT NULL`；
- `started_at TEXT NOT NULL`；
- `completed_at TEXT NULL`；
- `run_status TEXT NOT NULL`；
- `reused INTEGER NOT NULL`；
- 本次观察到的分层哈希；
- 有界知识元数据摘要；
- `warning_count INTEGER NOT NULL`；
- `failure_code TEXT NULL`。

运行状态至少包括：

- `started`；
- `completed_computed`；
- `completed_reused`；
- `failed`；
- `interrupted`。

失败记录不保存 Token、远程响应正文、原始异常或完整 PATH。

### 9.4 `snapshot_packages`

- `snapshot_id`；
- `scope`：`environment` 或 `lock`；
- 原始包名和规范化包名；
- 版本与版本有效性；
- 来源类型；
- 安全规范化后的来源身份；
- 确定性 `component_key`；
- 能确定时的直接依赖标记；
- 适用性状态。

同一包的多个版本分别保存。

### 9.5 `snapshot_dependencies`

- `snapshot_id`；
- `parent_component_key`；
- `child_component_key`；
- `relationship_source`；
- `resolution_status`。

只保存能够唯一确定且两端组件都存在的依赖边。

### 9.6 `snapshot_findings`

- `snapshot_id`；
- `scope`；
- 包名、规范化包名和被审计版本；
- GHSA、CVE 和稳定公告身份；
- 严重程度与 CVSS；
- 受影响范围与修复版本；
- `affected` 或 `indeterminate`；
- 无法判断原因；
- 公告内容指纹。

### 9.7 `snapshot_issues`

保存锁文件解析、多版本歧义、未解析依赖、知识库质量、截断和数据源健康问题的稳定错误码与有界主体。

### 9.8 `run_diffs`

固定差异锚点：

- `diff_id TEXT PRIMARY KEY`；
- `project_id TEXT NOT NULL`；
- `baseline_run_id TEXT NULL`；
- `target_run_id TEXT NOT NULL`；
- `diff_contract_version TEXT NOT NULL`；
- `classification TEXT NOT NULL`；
- 摘要计数；
- 压缩差异 JSON、原始长度和 SHA-256；
- `created_at TEXT NOT NULL`。

同一基线、目标和差异契约版本只保存一份。

### 9.9 索引

至少建立：

- `audit_runs(project_id, audit_kind, completed_at DESC)`；
- `audit_runs(snapshot_id)`；
- `audit_snapshots(project_id, audit_kind, created_at DESC)`；
- `audit_snapshots(project_id, audit_kind, composite_hash)`；
- `snapshot_packages(snapshot_id, scope, normalized_name, version)`；
- `snapshot_findings(snapshot_id, normalized_name, ghsa_id)`；
- `snapshot_findings(ghsa_id, cve_id, normalized_name)`；
- `snapshot_dependencies(snapshot_id, parent_component_key)`；
- `run_diffs(project_id, baseline_run_id, target_run_id)`。

历史查询不解析压缩 JSON。

## 10. 哈希规范

所有哈希对象使用 UTF-8 规范 JSON：键排序、固定分隔符、数组确定性排序、禁止 NaN，并包含域名称和哈希格式版本。

### 10.1 环境哈希

包含：

- 目标 Python 实现；
- 目标 Python `(major, minor, micro)`；
- 规范化包名、版本、版本有效性和歧义状态；
- 会影响审计完整性的稳定清点问题码。

不包含环境路径、可执行文件路径或 metadata 路径。

显式目标环境的 Python 版本优先从受控读取的 `pyvenv.cfg` 等环境元数据获得；不得错误使用运行 Svarog 的解释器版本代替目标版本。只有目标就是当前运行环境时才能使用 `sys.version_info`。无法可靠确定时写入 `unknown` 并产生问题记录。

### 10.2 锁文件语义哈希

包含锁格式、所有规范化包名与不同版本、版本有效性、来源类型、安全来源身份、稳定解析问题码以及能够确定的依赖边。

明确忽略：

- TOML 排版、注释、条目顺序和换行；
- marker 的适用性求值；
- 锁文件绝对路径。

marker 策略固定为 `ignored`，版本策略固定为 `all_distinct_versions`。

### 10.3 知识内容哈希

包含会改变匹配或报告内容的公告字段：包、GHSA/CVE、状态、撤回、范围、修复版本、严重程度、CVSS、摘要和来源。

不对 SQLite 文件字节计算哈希，避免 WAL、vacuum 和页布局造成虚假变化。

### 10.4 知识元数据与评估上下文

`knowledge_metadata_hash` 包含同步时间、同步状态、说明、来源集合和公告更新时间，不直接决定内容快照。

但知识库健康状态会影响审计警告和完成状态，因此另行计算 `evaluation_context_hash`，只使用稳定健康分组，例如：

- `healthy`；
- `stale`；
- `future_skew`；
- `invalid_sync_time`；
- `sync_failed`。

同步时间改变但健康分组未改变时复用快照；跨越七天新鲜度阈值等导致健康分组改变时重新生成快照。

### 10.5 策略与分析契约

`policy_hash` 包含 marker、版本选择、撤回公告、明细上限和知识新鲜度阈值。

`analysis_contract_version` 只在解析、匹配、分类或报告语义变化时升级。CSS 和普通文案变化不升级。

### 10.6 复合哈希

项目审计由以下内容组成：

```text
environment_hash
semantic_lock_hash
knowledge_content_hash
evaluation_context_hash
policy_hash
analysis_contract_version
audit_kind
hash_schema_version
```

环境审计省略 `semantic_lock_hash`。

`knowledge_metadata_hash` 不进入复合哈希。

## 11. 无变化复用和并发

耗时读取、哈希和匹配均在写事务之外完成。保存时：

1. `BEGIN IMMEDIATE`；
2. 再次查询 `(project_id, audit_kind, composite_hash)`；
3. 命中时更新 `last_used_at` 并保存 `completed_reused` 运行；
4. 未命中时保存快照、规范化表和 `completed_computed` 运行；
5. 提交事务。

唯一约束冲突时只捕获 `sqlite3.IntegrityError`，回滚后重新查询完全相同的复合哈希。确有快照才转为复用，其他约束错误必须失败，不能伪装成并发命中。

每次成功运行都固定 `baseline_run_id` 为同项目、同审计类型的上一次成功运行。以后新增运行不会改变既有差异含义。

## 12. 压缩结果与缓存

完整权威 JSON 以 zlib BLOB 保存，同时保存未压缩长度和 SHA-256。

统一读取接口 `get_snapshot_result(snapshot_id)`：

- 在解压前检查声明长度上限；
- 有界解压，拒绝超限数据；
- 校验原始长度与 SHA-256；
- 长期 Web 进程内使用容量为 5 的 LRU；
- 快照删除后清除对应缓存；
- 列表、搜索和差异查询不调用该接口。

## 13. 差异模型

首次运行分类为 `initial_snapshot`。已有历史时主分类为：

- `no_change`；
- `project_changed`；
- `knowledge_changed`；
- `project_and_knowledge_changed`。

仅知识元数据变化合并到 `no_change`，并显示固定备注。分析契约变化使用独立布尔字段，不伪装为项目或知识变化。

项目差异包括：

- Python 实现和版本；
- 环境包新增、删除、升级、降级、无效版本和多版本歧义；
- 锁定包新增、删除、版本集合和来源类型；
- 环境与锁文件匹配、缺失、意外安装和歧义状态；
- 已解析依赖边新增与删除；
- 未解析依赖问题变化。

漏洞差异包括：

- 新增、消失、持续和内容变化；
- `affected` 与 `indeterminate` 变化；
- 严重程度、CVSS、范围、修复版本和撤回状态变化。

“漏洞消失”只陈述目标快照不再匹配，并说明可能原因来自项目、知识库、分析契约或多个因素，不自动声称项目已经修复。

默认 UI 比较最新成功运行与固定的上一次成功运行。手动对比只允许同项目、同审计类型的兼容快照。反向选择时新增和删除方向必须反转。

## 14. CycloneDX 1.7 SBOM

### 14.1 输出范围

项目审计快照可以导出 CycloneDX 1.7 JSON：

- `metadata.component` 表示根项目；
- `components` 表示所有有效锁定组件；
- `dependencies` 表示能够唯一解析的依赖边；
- `compositions` 表示依赖图完整性；
- 不输出 `vulnerabilities`。

纯环境审计在 v0.2 不提供完整 SBOM 导出入口。

### 14.2 可重现性

- 使用快照创建时间，不使用下载时间；
- serial number 使用由项目 ID、复合哈希、规范版本和 SBOM 契约版本生成的 UUIDv5；
- 组件、依赖、properties 和 `dependsOn` 确定性排序；
- 固定 UTF-8、缩进和换行；
- 相同快照重复导出的文件字节及 SHA-256 相同。

### 14.3 `bom-ref`

- PyPI 包优先使用 `pkg:pypi/<name>@<version>`；
- 非 PyPI 包使用 `urn:svarog:component:sha256:<digest>`；
- 摘要只使用规范化名称、版本、来源类型和可用的不可变 revision/制品摘要；
- 禁止使用绝对路径、用户名、凭据、盘符、主机临时信息或时间戳；
- 允许字段仍无法区分两个组件时合并并产生警告，不通过本地路径制造虚假身份。

### 14.4 依赖边

只有父依赖声明能够唯一定位到一个锁定组件时才建立边。同名多版本、忽略 marker 后的多候选、来源冲突、目标缺失或未知结构均记录为未解析。

明确无依赖的组件输出空 `dependsOn`。无法确定是否有依赖的组件不伪装成空依赖，并通过 `compositions` 标记为 `unknown` 或 `incomplete`。

由于 v0.2 不读取 `pyproject.toml`，根项目的直接依赖通常无法完全确认，不生成“根项目依赖全部锁定包”的虚假关系。

### 14.5 离线 Schema

项目保存 CycloneDX 1.7 主 Schema、所有被引用子 Schema 和 `SHA256SUMS`。运行时副本作为 `svarog.sbom` 的 package data 安装：

```text
src/svarog/sbom/schemas/cyclonedx/1.7/
├─ bom-1.7.schema.json
├─ jsf-0.82.schema.json
├─ spdx.schema.json
├─ cryptography-defs.schema.json
└─ SHA256SUMS
```

测试目录保留一份锁定基准，用于确认打包资源未被意外替换：

```text
tests/fixtures/cyclonedx/1.7/
├─ bom-1.7.schema.json
├─ jsf-0.82.schema.json
├─ spdx.schema.json
├─ cryptography-defs.schema.json
└─ SHA256SUMS
```

两份资源的 SHA-256 必须一致。运行时使用成熟 JSON Schema 校验库进行离线验证，不实现不完整的自制验证器。Schema 摘要不一致或验证失败时不提供下载。

导出前额外检查 `bom-ref` 唯一、所有依赖引用有效、无绝对路径、无 URL 凭据、无控制字符并满足输出大小上限。

## 15. 历史保留

默认 180 天，合法范围 3 至 365 天。每次成功保存或复用审计后开启独立清理事务：

1. 删除超过保留期的旧运行记录；
2. 删除不再被保留运行引用、且 `last_used_at` 已过期的快照及其明细；
3. 每个项目、每种审计类型至少保留一个最新快照；
4. 清除已删除快照的 LRU 项；
5. 返回清理的运行和快照数量。

清理失败不回滚刚完成的审计，只返回警告。已经导出的文件不自动删除。

## 18. 端到端数据流

### 18.1 启动

1. 解析并固定 workspace；
2. 创建缺失的 `.svarog` 分类目录；
3. 读取项目身份和设置；
4. 安全打开并迁移审计历史库；
5. 检测旧案件库并按非破坏策略迁移；
6. 发现可信功能模块；
7. 启动仅回环地址可访问的 UI。

配置或历史库故障不能导致自动覆盖。写入能力不可用时，允许进入明确标记的只读历史查看模式；核心数据库无法安全读取时对应页面失败，其他独立页面继续工作。

### 18.2 审计

1. UI 验证相对路径和数据源选择；
2. 第一次项目审计先建立项目身份；
3. 读取目标环境、锁文件和稳定漏洞快照；
4. 计算分层哈希；
5. 命中复合哈希时复用，未命中时执行匹配；
6. 原子保存运行、快照和规范化明细；
7. 固定基线并生成差异；
8. 在独立事务中执行保留清理；
9. 返回审计摘要、变化分类和清理统计。

浏览器等待期间只显示“审计中”，不显示虚假百分比。按钮禁用，避免同一页面重复提交；数据库唯一约束继续作为跨窗口并发保险。

### 18.3 对比

1. 验证两个对象属于同一项目和审计类型；
2. 检查 Schema 与差异契约兼容性；
3. 查询规范化表计算差异；
4. 保存或复用固定 `run_diffs`；
5. 返回结构化 JSON 供 UI 渲染。

### 18.4 SBOM

1. 读取项目审计快照组件和依赖边；
2. 生成确定性 CycloneDX JSON；
3. 使用本地 Schema 验证；
4. 执行额外引用和隐私检查；
5. 计算最终 SHA-256；
6. 验证成功后提供下载。

## 19. 错误处理

### 19.1 用户输入错误

在字段旁显示简短原因并保留输入，不创建运行记录。示例：锁文件类型错误、路径逃逸、保留天数越界。

### 19.2 审计失败

已经开始实际读取后失败时保存 `failed` 运行及稳定错误码，不保存原始异常、密钥或远程正文。UI 显示简短错误和默认折叠的错误码。

### 19.3 数据库错误

- busy timeout 后返回“历史数据库正被占用”；
- 完整性或版本错误进入只读/拒绝写入状态；
- 迁移失败保留原库和备份；
- 不通过删除数据库来恢复。

### 19.4 清理错误

审计成功结果不回滚，只显示“审计已保存，但历史清理未完成”。

### 19.5 SBOM 错误

零有效组件、Schema 验证失败、引用无效或输出超限时不提供下载，原审计快照不受影响。

任何浏览器错误都不得包含 Python 堆栈、SQL、Token、Authorization、绝对路径或远程响应正文。

## 20. 测试策略

继续执行“冒烟测试早于编码”和小步 TDD。

### 20.1 数据库

- 创建、关闭、重开、版本验证；
- 迁移幂等与失败回滚；
- 高版本拒绝写入；
- 损坏库不覆盖；
- 并发相同快照只保存一次；
- 失败和中断运行状态；
- 3、180、365 天边界；
- 始终保留至少一个最新快照。

### 20.2 哈希与复用

- 固定 fixture 对应固定 SHA-256；
- 顺序、CRLF/LF 和绝对路径不影响语义哈希；
- 目标 Python 补丁版本变化改变环境哈希；
- marker 不过滤锁文件版本；
- 所有不同版本进入哈希；
- 同步时间变化只改变元数据哈希；
- 健康分组跨阈值改变评估上下文；
- 相同复合哈希复用快照。

### 20.3 差异

- 项目、知识、混合和无变化分类；
- 项目回退仍使用固定运行基线；
- 反向比较正确交换新增和删除；
- 漏洞撤回、严重度和修复版本变化；
- 分析契约变化不被误归因。

### 20.4 SBOM

- 固定输入产生固定文件 SHA-256；
- PURL 与非 PyPI `bom-ref`；
- 无路径、用户名和凭据；
- 引用完整性与唯一性；
- 已知叶子和未知关系正确区分；
- 多版本不生成虚假边；
- 循环依赖不递归崩溃；
- 零组件拒绝导出；
- 不包含 `vulnerabilities`；
- 使用固定 CycloneDX 1.7 Schema 完全离线验证；
- Schema 文件摘要变化时测试失败。

### 20.5 Web UI

- 路由、方法、CSRF、Host、Origin 和安全头；
- 分页和筛选上限；
- 双击提交保护；
- 服务重启后历史仍存在；
- 长包名和哈希不破坏布局；
- 键盘导航和焦点；
- 1280×720 Windows 浏览器验收；
- 页面不包含冗长教程、顶部宣传语或外部资源。

### 20.6 回归

- 现有日志分析、SOP、Python 审计、项目审计、Doctor 和可信模块测试全部通过；
- Windows 不支持的 POSIX 符号链接语义保持显式跳过，不伪装通过；
- 打包后的 Wheel 包含前端模块、Schema 和必要资源；
- 干净虚拟环境中安装、导入、启动和静态资源检查通过。

## 22. v0.2 验收标准

1. 同一项目、环境、锁文件、知识内容和评估上下文连续审计只产生一个内容快照和多条运行记录；
2. 两个并发审计不会向用户暴露 SQLite 唯一约束错误；
3. 知识同步时间变化但内容与健康分组未变时归入 `no_change`；
4. 项目变化、知识变化和共同变化能够分别识别；
5. 用户可以在 UI 查看历史、默认比较上一次并手动选择快照；
6. 保留天数可设为 3 至 365，默认 180，且始终保留最新快照；
7. 同一快照重复导出的 CycloneDX 文件字节完全一致；
8. SBOM 所有引用有效，不含漏洞对象、绝对路径、用户名或凭据；
9. 无法确定的依赖关系明确标为未知或不完整，不伪造成完整树；
10. UI 保持简洁，不包含页面内教程和冗长说明；
11. 现有功能和安全边界不回归；
12. Windows 普通用户按照最终文档可在五分钟内安装并打开 UI。
